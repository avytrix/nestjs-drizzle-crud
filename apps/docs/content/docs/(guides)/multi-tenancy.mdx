---
title: Multi-tenancy and ownership scoping
description: "Scope every read, count and write to a tenant or owner with one config key: scope: (ctx) => ({ tenant_id: ctx.tenantId }). Another tenant's id is a 404, and a missing tenant is a 403."
---

Set `scope` on an entity and every query the service runs is limited to the rows that match it: reads, counts, cursors, writes, bulk writes, upserts, soft deletes, restores and force deletes. A create writes the scope onto the new row. You cannot forget it in one place, because no method runs without it.

```ts accent=nest title="projects.crud.ts"
export const projectsCrud = {
  scope: (ctx) => ({ tenant_id: ctx.tenantId }),
} satisfies CrudFeatureConfig;
```

## What does a scope look like?

`column: value` pairs, each an exact match (`null` means `IS NULL`). Either fixed, or a function of the call's context:

```ts
scope: { region_id: 1 }                                   // fixed
scope: (ctx) => ({ tenant_id: ctx.tenantId })             // per request
scope: (ctx) => ({ tenant_id: ctx.tenantId, owner_id: ctx.userId })
scope: (ctx) => (ctx.isAdmin ? null : { tenant_id: ctx.tenantId })
```

Returning `null` leaves that call unscoped on purpose, for an admin or a background job. A key that is not a column throws. The function runs synchronously, so resolve anything async (the user, their tenant) in middleware and put the result in the context.

## Where does the context come from?

From `options.context` on the call, or else from `CrudContext`, which keeps a per-request value in Node's `AsyncLocalStorage` so it follows the request through every `await`:

```ts accent=nest title="projects.module.ts"
import { type MiddlewareConsumer, Module, type NestModule } from '@nestjs/common';
import { CrudContext, DrizzleCrudModule } from 'nestjs-drizzle-crud';

@Module({
  imports: [DrizzleCrudModule.forFeature([{ service: ProjectsService, table: projects, config: projectsCrud }])],
  controllers: [ProjectsController],
})
export class ProjectsModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(CrudContext.middleware((req) => ({ tenantId: req.user?.tenantId })))
      .forRoutes(ProjectsController);
  }
}
```

Outside a request, wrap the work yourself:

```ts
await CrudContext.run({ tenantId: 7 }, () => projects.findAll());
await projects.findAll({}, {}, { context: { tenantId: 7 } }); // per call, wins over CrudContext
CrudContext.current(); // the active context, or undefined
```

## What happens without a tenant?

The call fails closed. When the scope function returns `undefined` for a column (no tenant on the request), the service throws `MissingScopeException`, a 403, instead of running unscoped. A trusted server-side call can opt out with `skipScope: true`:

```ts
await projects.count({}, { skipScope: true }); // every tenant
```

## Which methods are scoped?

All of them:

| Area | Methods | Another tenant's row |
| --- | --- | --- |
| Reads | `find`, `findOne`, `exists`, `findAll`, `findByCursor`, `count`, `countBy`, `fullTextSearch`, relation `counts` | not found: `null`, `false`, or left out of the page and the total |
| Single writes | `update`, `softDelete`, `restore`, `delete`, `forceDelete` | 404 |
| Upsert | `upsert`, `massUpsert` | 404 (the conflicting row is not updated) |
| Bulk | `massUpdate`, `massSoftDelete`, `massRestore`, `massDelete`, `massForceDelete` | 400 with a 404 entry for that id, nothing written |
| Links | `attach`, `detach`, `sync` | 404 |

The scope is ANDed into the existence check and into the `UPDATE` or `DELETE` statement itself, so a row cannot change tenant between the two. On upsert it sits in the `ON CONFLICT DO UPDATE ... WHERE`, which MySQL does not have, so a scoped upsert on MySQL is a 400.

## What does a create or update do with the scope column?

`create`, `massCreate` and `upsert` write the scope values onto the row, over whatever the body said, so a client cannot create a row in another tenant. `update` never sets the scope columns: they are dropped from the `SET`, so a body cannot move a row to another tenant. An update whose only column was the scope column is a 400 (nothing to update).

With [nested create](/docs/relations-on-writes), child rows get the scope values too when their table has the same columns, and attach only links targets in the caller's tenant when the related table has the scope column.

## Are related tables scoped?

On reads, no. The scope applies to the service's own table; a relation loaded with `relations` or counted with `counts` follows its foreign key. That is safe when related rows always share the parent's tenant, which a foreign key usually guarantees. Give a related table its own service with its own scope when it is queried on its own.
