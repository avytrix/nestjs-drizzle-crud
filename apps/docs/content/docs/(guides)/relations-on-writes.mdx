---
title: Relations on writes, nested create, attach and detach
description: "Return created and updated rows with their relations loaded, create has-many and belongs-to children in one transaction, and attach, detach or sync many-to-many links."
---

`create`, `update`, `upsert`, `restore` and every mass write take `options.relations` and return the rows with those relations loaded, using the same batched loaders as a read. Nested create, behind `writableRelations`, writes children in the same transaction, and `attach`, `detach` and `sync` change many-to-many links with set-based statements.

## How do I get a created row back with its relations?

Pass `relations` (and `counts`, see [Aggregates](/docs/aggregates)) as you would on `find`:

```ts
const post = await posts.create(
  { title: 'Hello', author_id: 2, status: 'draft' },
  { relations: ['author', 'tags'] },
);
post.author.name; // 'Bob'
post.tags;        // []
```

That is one `INSERT` plus one query per relation. A mass write loads the relations of every row it wrote in one query per relation too, so `massCreate` of 10 posts with `relations: ['author']` is an `INSERT` and one `SELECT`, not ten.

```ts
const created = await posts.massCreate(dtos, { relations: ['author'], counts: ['tags'] });
```

`update`, `upsert`, `massUpsert`, `massUpdate`, `restore` and `massRestore` work the same way. The relation paths are checked against [`loadableRelations`](/docs/allowlists) before anything is written, so a bad path is a 400 and leaves the table untouched.

## How do I create a row with its children in one call?

List the relation in `writableRelations`, then put it in the body under the relation's name:

```ts accent=nest title="authors.module.ts"
DrizzleCrudModule.forFeature([{
  service: AuthorsService,
  table: authors,
  config: {
    relations: {
      posts: { table: posts, type: 'hasMany', foreignKey: 'author_id' },
    },
    writableRelations: ['posts'],
  },
}]);
```

```ts
const author = await authors.create(
  {
    name: 'Dee',
    email: 'dee@x.io',
    posts: [
      { title: 'First', status: 'draft' },
      { title: 'Second', status: 'draft' },
    ],
  },
  { relations: ['posts'] },
);
```

The author and both posts are written in one transaction: an `INSERT` for the author and one multi-row `INSERT` for the posts, with `author_id` set for you. If a child fails, the parent is rolled back and the call answers with the child's error (a bad enum value is a 400, a duplicate key a 409).

## What shapes does a nested body take?

| Relation | Body value | What happens |
| --- | --- | --- |
| has-many | an array of objects | One multi-row `INSERT`, with the foreign key set to the new row's key. |
| belongs-to | an object | The parent is inserted first and its key goes on the row (`localKey`). |
| many-to-many | an array of ids, objects, or both | Objects are inserted into the related table in one statement, then every id is linked through the join table. |

Nested writes are one level deep. Only the related table's own columns are written, never its soft delete column, and its timestamps and the [tenant scope](/docs/multi-tenancy) are set when the related table has those columns. Nested create needs `RETURNING`, so it runs on PostgreSQL; on MySQL it is a 400.

## What if writableRelations is not set?

Nested writes are off. A relation key in the body is left alone and Drizzle ignores it, which is how 3.4 behaved. With the list set, a relation key that is not in it is a 400, the same way [`writableColumns`](/docs/allowlists) treats a column.

## How do I attach or detach many-to-many rows?

```ts
await posts.attach(2, 'tags', [1, 2]);        // link tags 1 and 2
await posts.detach(2, 'tags', [1]);           // unlink tag 1
await posts.detach(2, 'tags');                // unlink every tag
const post = await posts.sync(2, 'tags', [2]); // links are exactly [2] now
post.tags; // [{ id: 2, name: 'tech' }]
```

Each method returns the row with that relation loaded (plus anything in `options.relations`) and runs in one transaction. They are set based whatever the number of ids: one `SELECT` checks the targets exist, one finds the links already there, and one `INSERT` adds the rest. Ids already linked are skipped, and duplicates in the list are ignored. The related rows themselves are never changed or deleted.

## What can go wrong?

- The row itself does not exist, or is outside the caller's [scope](/docs/multi-tenancy): 404.
- A target id that does not exist or is soft-deleted: a 400 `BulkOperationException` with one 404 entry per missing id.
- When the related table has the scope column, a target of another tenant counts as missing.
- The relation is not a many-to-many: 400.
- `writableRelations` is set and does not list the relation: 400. Unset, attach, detach and sync work on any many-to-many relation.

They raise `attach`, `detach` and `sync` [events](/docs/events) when global hooks are on.
