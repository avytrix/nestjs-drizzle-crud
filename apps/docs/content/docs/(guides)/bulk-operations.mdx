Bulk operations write the whole set with one statement, inside a single database transaction. If any item fails, the entire operation is rolled back and a `BulkOperationException` (400) is thrown. Its response body lists each failed item with its own status and message.

## The methods

```ts
await service.massCreate([dto1, dto2, dto3]);
await service.massUpdate([1, 2, 3], { status: 'archived' });
await service.massSoftDelete([1, 2, 3]);
await service.massRestore([1, 2, 3]);
await service.massDelete([1, 2, 3]);
await service.massForceDelete([1, 2, 3]); // soft-deleted rows too
await service.massUpsert(rows, { conflictTarget: 'email' }); // see Upsert
```

| Method | Returns | Failure mode |
| --- | --- | --- |
| `massCreate(data[], options?)` | `Promise<T[]>` | Tries every item, then throws `BulkOperationException` if any failed. |
| `massUpdate(ids[], data, options?)` | `Promise<T[]>` | Same. |
| `massSoftDelete(ids[], options?)` | `Promise<boolean>` | Same. |
| `massRestore(ids[], options?)` | `Promise<T[]>` | Same. |
| `massDelete(ids[], options?)` | `Promise<boolean>` | Same. |
| `massForceDelete(ids[], options?)` | `Promise<boolean>` | Same. Also deletes rows that are in the trash. |
| `massUpsert(data[], upsert, options?)` | `Promise<T[]>` | Same. See [Upsert](/docs/upsert). |

Duplicate ids are written once. The rows come back in the order of the ids you passed.

## How many queries does a bulk call cost?

A fixed number, whatever the number of ids:

| Method | Statements |
| --- | --- |
| `massCreate` | one multi-row `INSERT ... RETURNING` |
| `massUpdate` | one `SELECT` to check every id exists, one `UPDATE ... WHERE id IN (...)` |
| `massSoftDelete`, `massRestore` | one `SELECT`, one `UPDATE ... WHERE id IN (...)` |
| `massDelete`, `massForceDelete` | one `SELECT`, one `DELETE ... WHERE id IN (...)` |
| `massUpsert` | one `INSERT ... ON CONFLICT DO UPDATE` |

So `massUpdate` over 100 ids is two queries, not two hundred. Without `RETURNING` (MySQL) one more `SELECT` reads the rows back. On MySQL, `massCreate` of rows with auto-increment keys inserts row by row, because MySQL only reports the first id of a multi-row insert.

## Transactional semantics

All bulk methods wrap their work in a single transaction. If any row fails (constraint violation, FK error, validation, etc.), the transaction is rolled back. No partial writes are visible to subsequent reads.

When the set statement fails, the package needs to know which items caused it. It replays the batch one item at a time, each in its own savepoint, all inside an outer savepoint that is rolled back at the end, and reports the items that fail. That replay only runs on the failure path, and it leaves nothing behind even inside your own transaction. Two rows of the same batch that clash only with each other show up as the second of the pair, because the replay has already written the first. When no single item fails, the statement's own error is thrown instead.

<Callout type="info">
  A bulk operation that succeeds returns its full result. A bulk operation
  that fails throws `BulkOperationException` and **none** of the rows are
  modified. Use this as a guarantee, not just an optimization.
</Callout>

## Can I still run one query per item?

Yes, with `bulkMode: 'perItem'`. Each item then goes through the single-row method (`create`, `update`, `delete`, ...) in its own savepoint, as in 3.3. Use it when a per-item hook must see the rows written before it.

```ts
await service.massUpdate(ids, { status: 'archived' }, { bulkMode: 'perItem' });
```

## What does a failed bulk call return over HTTP?

A 400 whose body names every failed item. `massCreate` identifies an item by its `index` in the input array; the other methods use the `id` you passed:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Mass create errors. 1 error(s) occurred.",
  "errors": [
    { "index": 1, "status": 409, "message": "users with email 'ann@x.io' already exists" }
  ]
}
```

`status` and `message` are what that item alone would have produced: 409 for a duplicate, 404 for a missing id, 400 for bad input. An error that is not an HTTP exception (a driver fault, say) appears as `status: 500` with the message `Internal server error`, so SQL and parameters never reach the client. Let the exception propagate and Nest's default filter sends this body as is.

## `BulkOperationException` in code

```ts
import { BulkOperationException } from 'nestjs-drizzle-crud';

try {
  await users.massCreate([{ name: 'a', email: 'a@x.io' }, { name: 'b', email: 'taken@x.io' }]);
} catch (err) {
  if (err instanceof BulkOperationException) {
    // The original errors, one per failed item
    for (const { index, id, error } of err.errors) {
      console.error(`Item ${index ?? id} failed:`, error);
    }
    // The response body shown above
    console.log(err.getResponse());
  }
  throw err;
}
```

The `errors` property keeps the original `Error` objects for logging. The response body carries the safe summary.

## Lifecycle hooks during bulk operations

The standard `beforeCreate` / `afterCreate` (and the corresponding update / delete / softDelete / restore hooks) fire **once per row**, in array order. A `massCreate([a, b, c])` calls `validateCreate` and `beforeCreate` three times, then runs the one insert, then calls `afterCreate` three times. `massUpdate` checks the ids first, then calls `validateUpdate` and `beforeUpdate` once per id.

If any row's hook throws, that item is recorded as failed, the rest still run, and nothing is written. If `beforeUpdate` returns different data for different ids, one `SET` cannot express it, so `massUpdate` writes those rows with one `UPDATE` each.

## Passing options

All bulk methods accept the same `SqlOperationOptions` as their non-bulk counterparts. In particular, you can pass a custom transaction:

```ts
await service.executeSqlTransaction(async (tx) => {
  await service.massCreate(dtos, { transaction: tx });
  await otherService.massUpdate(otherIds, { flag: true }, { transaction: tx });
});
```

See [Transactions](/docs/transactions) for the full pattern.

## Limits and pagination

Bulk methods don't paginate. They accept the full array in memory and execute it as a single transaction. For very large bulk operations (thousands of rows), consider:

- **Chunking on the caller side**. Process arrays in batches of 100–500 rows and call `massCreate` per batch.
- **Switching to a streaming insert**. Write a custom method that uses Drizzle's `db.insert(...).values(chunk).execute()` chain with explicit chunking.

The cap is on the database side, not the package. Single transactions holding thousands of row locks can starve other connections.
