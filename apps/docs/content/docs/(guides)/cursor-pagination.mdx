---
title: Cursor (keyset) pagination
description: "findByCursor pages with WHERE (sort columns) > (last row) instead of OFFSET: constant cost on deep pages, stable under inserts, with an opaque nextCursor."
---

`findByCursor(filters, pagination, options)` returns a page plus an opaque `nextCursor`; pass that cursor back to get the next page. Each page is a `WHERE` on the sort columns instead of an `OFFSET`, so page 500 costs the same as page 1 and a row inserted on an earlier page does not shift the next one.

```ts
let cursor: string | null = null;
do {
  const page = await posts.findByCursor(
    { status: 'published' },
    { sortBy: ['-published_at'], limit: 50, cursor },
  );
  handle(page.data);
  cursor = page.nextCursor;
} while (cursor);
```

## What does a page look like?

```ts
interface CursorPage<T> {
  data: T[];
  limit: number;
  nextCursor: string | null;   // null on the last page
  total?: number;              // only with count: true
}
```

There is no `page` number: a cursor is a position, not an index. The count query is skipped unless you pass `count: true`, because counting is the slow part of a large list.

## Options

| Field | Default | Notes |
| --- | --- | --- |
| `cursor` | none | The `nextCursor` of the previous page. Absent, `null` or `""` means the first page. |
| `after` | none | Alias of `cursor`. |
| `limit` | `defaultLimit` | Capped at `maxLimit`. |
| `sortBy`, `sortOrder` | `defaultSort`, then the primary key | Same shapes as `findAll`, relation columns included. See [Pagination & sorting](/docs/pagination-sorting). |
| `count` | `false` | Also run the count query and return `total`. |

Filters, `options.search`, `select`, `relations`, soft delete scope and locks all work as they do in `findAll`.

## How does the cursor work?

It holds the sort values of the last row on the page, primary key last, as base64url JSON, plus the sort it was made for. The next query asks for rows after that position:

```sql
WHERE (views > $1) OR (views = $1 AND id > $2)
ORDER BY views ASC, id ASC
LIMIT 51
```

The primary key tiebreaker makes every position unique, so no row is repeated or skipped. One extra row is fetched to know whether there is a next page. NULLs follow the database's own ordering (last ascending and first descending on Postgres), and timestamp values keep their microseconds.

The cursor is opaque but not secret: anyone can decode it, so it only ever holds values the rows already show. A cursor that is not valid, or was made for a different sort, is a 400.

## Over HTTP

With [`parseQuery`](/docs/query-parsing), `?cursor=` (empty) starts a keyset walk and sets `isCursor`:

```txt
GET /countries?limit=20&cursor=
GET /countries?limit=20&cursor=eyJzIjoibmFtZTphc2MsaWQ6YXNjIiwidiI6WyJDaGFkIiw1MF19
GET /countries?limit=20&cursor=&count=true
```

## When should I use offset instead?

When the UI shows page numbers or jumps to page 7. Keyset pages only go forward from a known position. For infinite scroll, exports, sync jobs and any list that grows while people read it, use the cursor.
