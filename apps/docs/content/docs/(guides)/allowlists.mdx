---
title: Allowlists and secure defaults
description: "Limit which columns a client may filter, sort, select and search, which relations it may load, and which columns create and update may write. Anything else is a 400."
---

Allowlists decide what a client may touch through a query or a request body. Set them per entity in `forFeature`; anything outside a set list is a 400, both in the service and in [`parseQuery`](/docs/query-parsing).

```ts accent=nest title="users.module.ts"
DrizzleCrudModule.forFeature([
  {
    service: UsersService,
    table: users,
    config: {
      filterableColumns: ['status', 'role', 'created_at', 'team.name'],
      sortableColumns: ['name', 'created_at', 'team.name'],
      selectableColumns: ['id', 'name', 'email', 'team.name'],
      searchableColumns: ['name', 'email'],
      loadableRelations: ['team', 'projects.tasks'],
      writableColumns: ['name', 'email', 'role', 'team_id'],
    },
  },
]);
```

## Why should I set them?

Because a list endpoint that forwards the query string otherwise lets a client reach every column. Without `selectableColumns`, `?fields=password_hash` returns the hashes. Without `filterableColumns`, `?password_hash[startsWith]=a` lets a client guess one a character at a time. Without `writableColumns`, a body with `role: 'admin'` sets it, unless every DTO strips it. Set the lists on any entity a client can reach.

## What does each list cover?

| Key | Checked on | Entries |
| --- | --- | --- |
| `filterableColumns` | `findAll`, `findByCursor` and `count` filters, groups included | Columns, and `relation.column` for relation filters. |
| `sortableColumns` | a caller `sortBy` | Columns, and `relation.column` for a belongs-to. The primary key is always allowed. |
| `selectableColumns` | `options.select` on every read | Columns, and dotted paths at any depth (`states.cities.name`). The primary key is always allowed. |
| `searchableColumns` | `options.search.columns` and `fullTextSearch` | Columns. `parseQuery` also uses it as the default search columns. |
| `loadableRelations` | `options.relations` | Relation paths. Listing `states.cities` allows `states` too. |
| `writableColumns` | `create`, `update`, `upsert` and the mass versions | Columns. |

An unset list allows everything, which is how 3.3 behaved. An empty list (`[]`) allows nothing.

## What is not checked?

`findOne(where)` is usually a server-side lookup (`findOne({ email })` during login), so its `where` keys are not checked against `filterableColumns`; its `select` and `relations` are. The configured `defaultSort` is not checked either. For any other trusted call, pass `skipAllowlists: true`:

```ts
await users.count({ password_reset_token: token }, { skipAllowlists: true });
```

## Which columns can a body write by default?

Everything except the columns the package manages itself. Without `writableColumns`:

- the soft delete column is ignored on create and update,
- the primary key and the `createdAt` timestamp are ignored on update.

Ignored means dropped silently, so a `PATCH` body that echoes `id` back still works. An update that has nothing left to set is a 400.

With `writableColumns` set, any column outside the list is a 400 (`Validation failed: the column "role" is not writable`), the managed columns included. List the primary key there if your create path takes client supplied keys, such as uuids or natural keys. Keys that are not columns at all are ignored, as before.

## Recommended setup

1. Keep `ValidationPipe({ whitelist: true })` and real DTOs for request bodies.
2. Set `writableColumns` on every entity with a public create or update route.
3. Set `selectableColumns` and `filterableColumns` on every entity behind a list route, and leave secrets out of both.
4. Set `loadableRelations` when a related table holds data some callers must not see.
