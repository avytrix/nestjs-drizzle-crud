---
title: Soft delete
description: "Enable soft delete with a deleted_at column, restore rows, list the trash with onlyDeleted or withDeleted, and purge rows for good with forceDelete."
---

Soft delete sets a `deleted_at` timestamp on a row instead of removing it. Reads (`find`, `findOne`, `findAll`, `findByCursor`, `count`) exclude soft-deleted rows unless you pass `withDeleted` or `onlyDeleted`; `restore(id)` clears the column and brings the row back, and `forceDelete(id)` removes it for good.

## Enabling

### Globally (default for all entities)

```ts accent=nest title="app.module.ts"
DrizzleCrudModule.forRoot({
  dialect: 'postgresql',
  connectionString: process.env.DATABASE_URL,
  schema,
  defaults: { softDelete: true },   // default is already true
});
```

The package looks for a column under the key `deleted_at` by default. The setting names the **key in your Drizzle table object**, not the database column name. With a camelCase schema such as `deletedAt: timestamp('deleted_at')`, set `column: 'deletedAt'`.

<Callout type="warn" title="A missing column fails at startup">
  Since 3.3.1 the service checks the soft-delete column when it is built. If
  the table has no key by that name, startup fails with a message that names
  the key to use, for example: `softDelete.column is "deleted_at", but the
  table has no column under that key. The column "deleted_at" is declared
  under the key "deletedAt"; set softDelete.column to "deletedAt".`
  Before 3.3.1 the same mistake made every read fail with a 500.
</Callout>

### Per-entity (different column name or disable for one entity)

```ts accent=nest
DrizzleCrudModule.forFeature([
  {
    service: AuditLogService,
    table: auditLog,
    config: { softDelete: { enabled: false } },
  },
  {
    service: UsersService,
    table: users,
    config: { softDelete: { enabled: true, column: 'archivedAt' } },
  },
])
```

Per-entity config overrides the global default, and merges with it: `{ softDelete: { column: 'archivedAt' } }` keeps `enabled` from the project setting. The `column` is the key in your Drizzle table object; the package uses it in `WHERE` clauses and in `SET` / `UPDATE` statements.

## The methods

### `softDelete(id, options?)` → `Promise<boolean>`

```ts
const ok = await users.softDelete(42);
if (!ok) {
  // row didn't exist
}
```

Returns `true` if the row was found and marked deleted, `false` if it didn't exist.

### `restore(id, options?)` → `Promise<T>`

```ts
const restored = await users.restore(42);
// full row, with deleted_at = null
```

Throws `EntityNotFoundException` if the row didn't exist (or didn't have a soft-delete column set). Returns the restored entity on success.

<Callout type="info">
  `restore` is independent of soft-delete state. It will happily
  re-`restore` a row that wasn't soft-deleted (effectively a no-op on
  the column). To check whether a row is in the trash, read it with
  `onlyDeleted`: `await users.exists(42, { onlyDeleted: true })`.
</Callout>

### `massSoftDelete(ids, options?)` → `Promise<boolean>`

```ts
await users.massSoftDelete([1, 2, 3]);
```

Same as `softDelete` for a set of ids: one `SELECT` to check they exist and one `UPDATE ... WHERE id IN (...)`, in a transaction. If any id does not exist or is already in the trash, nothing changes and `BulkOperationException` lists the ids that failed. `massRestore(ids)` is the reverse.

### Reads automatically exclude soft-deleted rows

```ts
// excludes rows with deleted_at IS NOT NULL
await users.find(42);
await users.findOne({ email: 'ada@example.com' });
await users.findAll({});
await users.count({});
```

A belongs-to relation follows the same rule. When the related table has the soft-delete column, a soft-deleted parent comes back as `null` on an eager load, and a relation filter such as `{ author: { name: 'Bob' } }` does not match it.

## How do I list soft-deleted rows?

Pass `onlyDeleted: true` for the trash view, or `withDeleted: true` for live and deleted rows together. Both work on every read: `find`, `findOne`, `findAll`, `findByCursor`, `count`, `exists` and `fullTextSearch`.

```ts
// The trash, newest first
const trash = await users.findAll({}, { sortBy: '-deletedAt' }, { onlyDeleted: true });

// Everything, deleted or not
const all = await users.count({}, { withDeleted: true });

// Is this row in the trash?
const inTrash = await users.exists(42, { onlyDeleted: true });
```

The flags only change the service's own table. Related tables keep hiding their soft-deleted rows, so an eager-loaded parent that is in the trash still comes back as `null`. `onlyDeleted` on an entity without soft delete is a 400.

A filter on the column itself, such as `{ deletedAt: { isNotNull: true } }`, still returns nothing without one of the flags, because the default `deleted_at IS NULL` is ANDed with it.

Over HTTP, [`parseQuery`](/docs/query-parsing) reads `?onlyDeleted=true` and `?withDeleted=true`, but only when you opt in with `allowTrash: true`. Without it they are unknown filter columns, so a client cannot open the trash on a route that is not meant to show it.

```ts accent=nest title="users.controller.ts"
@Get('trash')
trash(@Query() query: Record<string, unknown>) {
  const q = this.users.parseQuery({ ...query, onlyDeleted: 'true' }, { allowTrash: true });
  return this.users.findAll(q.filters, q.pagination, q.options);
}
```

## How do I purge a soft-deleted row?

`forceDelete(id)` hard-deletes the row whether it is in the trash or not, and runs the delete hooks. `massForceDelete(ids)` does the same for a set of ids in one statement.

```ts
await users.forceDelete(42);           // gone, even if it was soft-deleted
await users.massForceDelete([7, 8, 9]); // one DELETE ... WHERE id IN (...)
```

`delete(id)` keeps its meaning: it only sees live rows, so it answers 404 for a row that is already in the trash. The same is true of `massDelete`. Both `delete` and `forceDelete` accept the same options, so `delete(id, { withDeleted: true })` is the long way of writing `forceDelete(id)`.

## The schema column

```ts accent=drizzle title="db/schema.ts"
import { pgTable, serial, varchar, timestamp } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  name: varchar('name', { length: 100 }).notNull(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  deletedAt: timestamp('deleted_at', { withTimezone: true }),
});
```

The column type should accept `null` (and the package will set it to `null` on `restore` and to `new Date()` on `softDelete`). This schema uses the camelCase key `deletedAt`, so its `forFeature` config needs `softDelete: { column: 'deletedAt' }`.

<Callout type="warn" title="If the column doesn't exist">
  If your table has no soft-delete column, set
  `defaults: { softDelete: false }` (or per-entity
  `config: { softDelete: { enabled: false } }`). Otherwise the service
  refuses to start and names the missing key.
</Callout>

## Soft delete + hard delete

The package exposes both `softDelete` and `delete`:

| Method | Behavior |
| --- | --- |
| `delete(id, options?)` | Hard delete, removes the row. Its existence check skips soft-deleted rows, so it answers 404 for a row that is already in the trash. |
| `forceDelete(id, options?)` | Hard delete, whether the row is in the trash or not. |
| `softDelete(id, options?)` | Sets `deleted_at = now()`. Reads afterwards exclude it. |
| `massDelete(ids, options?)` | Hard delete of live rows, one statement, transactional. |
| `massForceDelete(ids, options?)` | Hard delete of live and trashed rows, one statement, transactional. |
| `massSoftDelete(ids, options?)` | Soft delete, one statement, transactional. |

Use `delete` when you really want the row gone (e.g. GDPR right-to-erasure flows). Use `softDelete` when you want reversibility and audit trails.
